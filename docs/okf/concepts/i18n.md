# Internacionalização (i18n)

## Decisão

O app é internacionalizável desde a fundação: nenhuma string de UI é
hardcoded fora do mecanismo de i18n. Stack: `flutter_localizations` + `intl`,
arquivos `.arb` em `app/lib/l10n/` (`app_pt.arb` é o template/fonte,
`app_en.arb` a segunda locale), geração via `flutter gen-l10n` (config em
`app/l10n.yaml`, acionada automaticamente por `flutter pub get`/build via
`generate: true`). Acesso em runtime: `AppLocalizations.of(context)!`.

## Por quê

`pt` como locale-fonte porque é o idioma dos documentos do projeto
(SPEC/AGENTS); `en` mantido junto desde o início — não depois — porque ter
duas locales desde o começo é o que força o hábito de nunca hardcodar
string de UI. Retrofitting i18n depois que strings já estão espalhadas pelo
código é um projeto à parte; fazer desde o início custa quase nada.

## Onde isso vive no código

`app/l10n.yaml` (config), `app/lib/l10n/app_pt.arb` e `app_en.arb` (fonte),
`app/lib/l10n/gen/` (gerado, não versionado — ver `.gitignore`). Consumido
em `app/lib/ui/router.dart` e `app/lib/ui/screens/`.
