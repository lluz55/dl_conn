# Internacionalização (i18n)

## Decisão

O SPA (`web/`) é um app em **JavaScript puro**, sem framework e sem biblioteca
de i18n. As strings de UI estão em **`pt-BR` inline** (ver `lang="pt-BR"` em
`web/index.html`), escritas diretamente nos módulos `web/js/*.js` e em
`web/index.html`. Não há arquivos de localização gerados nem sistema de
localização centralizado hoje.

## Por quê

- O produto nasceu com foco no idioma dos documentos do projeto (pt-BR) e a
  superfície de texto do SPA é pequena e estável — um framework de i18n seria
  peso morto.
- Manter strings em **um lugar só** ainda é o objetivo: sempre que uma label de
  UI for adicionada, prefira referenciar uma constante central (ex.: um objeto
  `strings` em `web/app.js` ou `web/js/`) em vez de espalhar literais pelo DOM.

## Quando adicionar uma segunda locale

Se um segundo idioma se tornar necessário, **não** introduza um sistema de
geração de código de i18n:
escolha uma abordagem leve compatível com ES modules (ex.: um dicionário
`{ pt-BR: {...}, en: {...} }` importado pelos módulos, trocado por um
`data-locale` no `document.documentElement`). O princípio — nunca hardcodar
string de UI em múltiplos pontos — permanece o mesmo.

## Onde isso vive no código

`web/index.html` (`lang="pt-BR"`, markup), `web/app.js` e `web/js/*.js`
(labels inline). Consumido na renderização do dashboard em
[web-frontend-layout.md](web-frontend-layout.md).

Relacionado: [theming.md](theming.md) (mesma lógica de "nunca hardcode, sempre
token/recurso central" aplicada a texto e estilo).
